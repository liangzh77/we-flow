# 下一步验证计划：微信消息读取与 AI 分析

日期：2026-05-19

## 当前共识

第一阶段先做“读取微信消息 + AI 分析 + 回复草稿”，不直接做自动发送。

原因：

- `wx-cli` 已验证可以初始化并读取本机微信数据。
- 读取和分析链路可行性高。
- 自动发送微信存在更高风险，应该单独验证，并且默认需要人工确认。

## 下一步目标

验证 `wx-cli` 能否稳定支持第一阶段 MVP 所需的数据能力。

第一阶段 MVP 目标：

- 获取新消息
- 区分群聊和一对一聊天
- 获取消息发送人、时间、内容、消息类型
- 将消息结构化存储
- 用 AI 生成摘要、待办、重点提醒和回复建议

## 已确认的 wx-cli 接口

### new-messages

```powershell
wx new-messages --json
```

用途：获取自上次检查以来的新消息。

可用参数：

- `--limit <LIMIT>`：显示数量上限，默认 200
- `--json`：输出 JSON
- `--with-meta`：返回更重的元数据

需要验证：

- 是否真的只返回增量消息
- cursor 存在哪里
- 多次调用是否会重复
- 微信重启后是否还能接续
- 延迟是多少
- 是否会漏消息

### sessions

```powershell
wx sessions -n 20 --json
```

用途：列出最近会话。

需要验证：

- 是否包含会话 ID
- 是否包含会话名称
- 是否能区分群聊、私聊、公众号、折叠会话
- 是否有最后消息时间
- 是否有未读数量

### history

```powershell
wx history <CHAT> -n 20 --json
```

用途：查看某个聊天对象的聊天记录。

可用参数：

- `--limit <LIMIT>`：消息数量
- `--offset <OFFSET>`：分页偏移
- `--since <SINCE>`：起始日期，格式 `YYYY-MM-DD`
- `--until <UNTIL>`：结束日期，格式 `YYYY-MM-DD`
- `--type <TYPE>`：消息类型过滤
- `--json`：输出 JSON

支持的消息类型：

- `text`
- `image`
- `voice`
- `video`
- `sticker`
- `location`
- `link`
- `file`
- `call`
- `system`

需要验证：

- 私聊和群聊的输出结构是否一致
- 消息是否有稳定 ID
- 是否包含发送人
- 是否能识别自己发出的消息
- 群聊中是否能识别具体群成员
- 非文本消息如何表示

### members

```powershell
wx members <CHAT> --json
```

用途：查看群成员。

需要验证：

- 是否能通过群聊名称模糊匹配
- 是否包含成员 ID
- 是否包含昵称、备注、群昵称
- 是否能和 `history` 中的发送人字段对应

## 建议的验证顺序

### 第 1 步：结构探针

目标：只看 JSON 结构，不展开隐私正文。

建议命令：

```powershell
wx sessions -n 10 --json
wx new-messages -n 10 --json
```

处理方式：

- 只记录顶层字段
- 只记录数组长度
- 对消息对象只记录字段名
- 不记录聊天内容、联系人名称、群名称

判断标准：

- 能拿到会话列表
- 能拿到新消息列表
- 每条消息字段足够支撑后续分析

### 第 2 步：实时性验证

目标：确认 `new-messages` 能否作为实时或准实时入口。

实验方式：

1. 先运行一次 `wx new-messages -n 10 --json`，清空当前增量窗口。
2. 从手机或另一个微信账号发送一条测试消息。
3. 每 5 秒运行一次 `wx new-messages -n 10 --json`。
4. 记录首次出现该消息的时间。
5. 连续发送 5 条消息，检查是否漏读、乱序、重复。

判断标准：

- 延迟小于 10 秒：可以视为实时。
- 延迟 10 秒到 60 秒：可以视为准实时。
- 延迟超过 60 秒或不稳定：第一版改成定时扫描。

### 第 3 步：群聊与私聊字段验证

目标：确认是否能区分群聊和私聊，以及群聊发送人。

建议选择：

- 一个低风险私聊测试对象
- 一个低风险群聊测试对象

建议命令：

```powershell
wx history <私聊名称> -n 5 --json
wx history <群聊名称> -n 5 --json
wx members <群聊名称> --json
```

处理方式：

- 不保存原始内容
- 只记录字段名、字段类型、是否为空
- 对发送人、会话名做脱敏

判断标准：

- 私聊能识别对方和自己
- 群聊能识别具体发送人
- 群成员能和消息发送人关联

### 第 4 步：消息类型验证

目标：确定第一版支持哪些消息类型。

建议先验证：

```powershell
wx history <CHAT> --type text -n 5 --json
wx history <CHAT> --type link -n 5 --json
wx history <CHAT> --type image -n 5 --json
wx history <CHAT> --type file -n 5 --json
```

第一版建议：

- 支持文本消息
- 支持链接消息的标题和 URL，如果能读到
- 图片、语音、文件先作为非文本事件记录
- 不做语音转文字和图片 OCR，除非后续明确需要

### 第 5 步：本地存储设计验证

目标：确认是否能构造稳定去重 key。

需要检查每条消息是否有：

- 原始消息 ID
- 会话 ID
- 时间戳
- 发送人 ID
- 消息类型
- 内容

如果有稳定消息 ID：

- 用消息 ID 作为主键。

如果没有稳定消息 ID：

- 使用 `conversation_id + sender_id + timestamp + type + content_hash` 生成去重 key。

建议本地存储：

- SQLite
- 表：`messages`
- 表：`conversations`
- 表：`analysis_reports`
- 表：`reply_drafts`

### 第 6 步：最小 AI 分析链路

目标：证明聊天记录能变成有价值的 AI 输出。

最小输入：

- 最近 1 小时新消息
- 或指定会话最近 50 条文本消息

最小输出：

- 重点摘要
- 待办事项
- 需要回复的人
- 风险或重要提醒
- 回复建议草稿

第一版报告格式：

```markdown
# 微信消息摘要

## 重要事项

## 待办

## 需要回复

## 回复建议

## 低优先级信息
```

## 自动发送微信的后续验证

自动发送不进入第一阶段。

后续单独验证：

- `wx-cli` 是否存在发送命令
- 微信桌面客户端是否能通过 UI 自动化填入消息
- 是否能做到“填入输入框但不发送”
- 是否能加二次确认
- 是否存在微信风控风险

建议发送能力分级：

1. 生成回复草稿。
2. 用户确认后填入微信输入框。
3. 用户再次确认后发送。

不建议一开始允许 AI 无确认自动发送。

建议产物：
